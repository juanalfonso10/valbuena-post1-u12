# ADR-001: Capas simples para la persistencia; el seam de notificación ya cubre el próximo cambio conocido

## Estado
Aceptado — 2026-11-06

## Contexto
El sistema de solicitudes de reembolso ya integra Chain of Responsibility (validación), Strategy
(cálculo) y Observer (notificación). `SolicitudReembolsoService` depende directamente de
`RepositorioSolicitudesJpa`, un `JpaRepository` de Spring Data, y notifica a los interesados a
través de la interfaz `ObservadorCambioEstado`.

La pregunta es si el sistema debe migrar a arquitectura Hexagonal completa, con puertos e
interfaces intermedias para todas sus dependencias externas, o mantenerse en capas simples. La
Guía (sección 6.2) da el criterio: la Hexagonal vale la pena en sistemas que sobrevivirán 3 años
o más con cambios de infraestructura. El criterio se evalúa por separado para cada dependencia
externa, con los datos que hoy tiene el proyecto:

| Dependencia | ¿Hay un cambio de infraestructura real y fechado? | Punto de extensión que ya existe |
|---|---|---|
| Persistencia | No. No hay ningún plan de cambiar el motor de base de datos. | Solo `SolicitudReembolsoService` usa el repositorio, y el dominio no tiene anotaciones JPA (el mapeo está en `orm.xml`). |
| Notificación | Sí. Contabilidad anunció para el próximo trimestre una integración por API externa para pagar las solicitudes aprobadas. Finanzas pidió también un panel de métricas. | `ObservadorCambioEstado`: el servicio no conoce a ningún notificador concreto. |

## Alternativas consideradas

**A. Hexagonal completa.** Puerto `RepositorioSolicitudes` en el dominio con un adaptador JPA en
infraestructura, más un puerto para cada canal de notificación.
- A favor: simetría total y motor de base de datos intercambiable.
- En contra: agrega una interfaz, un adaptador y, si se separa la entidad JPA del dominio, un
  mapper y una clase duplicada, todo para un cambio que nadie pidió. Es la abstracción
  especulativa que YAGNI desaconseja.

**B. Puerto solo para la persistencia.** Igual a A pero dejando la notificación como está.
- En contra: concentra el esfuerzo justo en la dependencia que no va a cambiar, y no aporta
  nada a la que sí cambiará.

**C. Capas simples, apoyándose en el seam que ya existe para la notificación (elegida).**
- A favor: cero código adicional hoy; el único cambio con fecha ya tiene su punto de extensión.
- En contra: ver Consecuencias.

## Decisión
Se mantiene la arquitectura en capas simples. `SolicitudReembolsoService` sigue dependiendo
directamente de `RepositorioSolicitudesJpa`, sin un puerto intermedio: para la persistencia el
criterio de la sección 6.2 no se cumple, porque no hay ningún cambio de infraestructura previsto.

Para la notificación tampoco se introduce ningún cambio. `ObservadorCambioEstado` ya cumple el
papel de puerto: el servicio publica el cambio de estado sin saber quién lo recibe. Cuando llegue
la integración de Contabilidad, su implementación con el cliente HTTP de la API externa se
ubicará en `infraestructura` (por ejemplo, `infraestructura.contabilidad.NotificadorPagosApi
implements ObservadorCambioEstado`) y reemplazará a `NotificadorContabilidad`. No habrá que
modificar `SolicitudReembolsoService` ni los demás observadores. El panel de métricas será, del
mismo modo, un observador más.

## Consecuencias

Positivas:
- No se agregan interfaces, adaptadores ni mappers de persistencia sin un caso de uso que los
  justifique.
- El único cambio de infraestructura con fecha conocida, la integración de Contabilidad, ya
  tiene su punto de extensión listo y verificado por la Regla 4 de `ReglasArquitectura`.
- Si algún día hiciera falta el puerto de persistencia, el costo está acotado: un solo servicio
  usa el repositorio y el dominio ya es independiente de JPA gracias a `orm.xml`.

Negativas:
- Un cambio de motor de base de datos obligaría a introducir el puerto de forma retroactiva. Se
  acepta esa deuda técnica conscientemente.
- La asimetría (la notificación desacoplada y la persistencia no) puede parecer inconsistente a
  un revisor que espere puertos en todas las dependencias externas si no lee este ADR.
- Spring Data queda visible en la capa de aplicación: `SolicitudReembolsoService` importa un tipo
  que extiende `JpaRepository`.

## Cuándo revisar esta decisión
- Si se aprueba migrar de motor de base de datos, o si aparece un segundo almacenamiento (por
  ejemplo, un histórico en otro sistema), introducir el puerto `RepositorioSolicitudes`.
- Si el sistema necesita probarse sin Spring Data en la capa de aplicación (por ejemplo, para
  ejecutar el servicio contra un almacenamiento en memoria), reevaluar la alternativa A.
